# 公告未读弹窗与已读红点设计

## 目标

当系统存在当前用户尚未阅读的可见公告时，自动打开公告列表弹窗，并在公告入口显示红点。用户点击公告入口打开列表后，将当前可见公告标记为已读，红点立即消失。后续发布新的可见公告时，仅新公告再次触发提示。

## 当前实现

- 服务端已有 `/api/announcements` 路由和公告 CRUD。
- 客户端已有 `AnnouncementPopover`，负责加载公告、显示公告列表和管理员操作。
- 当前红点仅判断公告列表长度，因此已读状态无法区分，也没有自动弹窗。
- 公告路由在 `api/server/routes/announcements.js` 内定义 Mongoose 模型，第一版沿用该模块边界。

## 方案

新增独立的用户级已读记录集合，不修改公告文档和用户文档。

已读记录字段：

- `userId`：已认证用户 ID
- `announcementId`：公告 ID
- `readAt`：最近一次标记已读时间

在 `userId + announcementId` 上建立唯一索引。标记已读使用幂等批量写入，允许重复请求和多窗口并发。

## 服务端接口

### `GET /api/announcements`

保持现有公告数组响应，并为每条公告增加 `unread: boolean`：

- 可见公告在当前用户没有已读记录时为 `true`。
- 停用公告或未到发布时间的公告始终不触发未读状态。
- 管理员通过 `all=true` 查看额外公告时，额外公告仍可出现在列表中，但不影响红点。

### `POST /api/announcements/read`

接收当前用户需要标记的公告 ID 列表。服务端重新查询并过滤当前用户可见的公告，只为有效记录执行幂等批量写入，防止客户端伪造公告 ID 或标记不可见公告。

现有管理员发布、更新、停用和删除接口保持不变。

## 前端流程

`AnnouncementPopover` 继续作为公告入口和列表组件，并增加以下行为：

1. 组件加载后获取公告列表，计算可见未读公告。
2. 存在未读公告时自动打开公告列表弹窗。
3. 弹窗通过手动点击或自动打开时，执行“打开即已读”，调用批量已读接口。
4. 已读请求成功后立即清除本地未读状态，入口红点消失。
5. 用户再次打开入口时仅显示公告列表，不会重复自动弹窗。
6. 浏览器窗口重新获得焦点时重新加载公告，以发现页面停留期间发布的新公告；第一版不引入 WebSocket 或持续轮询。

如果已读请求失败，公告列表仍保持可用，但红点保留；下一次打开入口或窗口重新聚焦时重试。

## 权限与生命周期

- 已读记录始终按认证用户隔离。
- 新用户没有任何已读记录，因此会收到当前可见公告提示。
- 删除公告后，其已读记录可以保留，不影响后续公告；不增加本次需求之外的清理任务。
- 新公告使用新的公告 ID，自然不会命中旧的已读记录。

## 测试

### 服务端

- 未读公告只对当前用户返回 `unread: true`。
- 同一公告重复标记已读不会重复创建记录。
- 标记已读接口忽略不存在、不可见或无权限公告 ID。
- 停用公告和未到发布时间的公告不会触发未读状态。

### 客户端

- 有未读公告时自动打开列表并显示红点。
- 打开列表后成功标记已读，红点消失。
- 已读公告再次加载时不自动弹窗。
- 标记已读失败时红点保留，并可在后续操作中重试。
- 管理员可以继续管理额外公告，但额外公告不影响红点。

## 非目标

- 不新增公告管理页面。
- 不改变现有公告管理权限。
- 不实现实时推送。
- 不把已读 ID 写入用户文档或浏览器本地存储。
